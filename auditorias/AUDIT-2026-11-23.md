## 1. Veredicto

**No se puede abrir a usuarios reales todavía, pero no por el código: por lo que falta alrededor de él.** El código es sólido (tsc y lint en verde, 2 081 pruebas unitarias, RLS con initplan y `search_path` correctos en el 100 % de lo revisado, 2FA de admin en app y base, ningún secreto en git). #### P1-2 · Un estudiante puede reescribir `correo`, `foto_url`, `slug` y `anonimizado_en` de su perfil sin pasar por la app

| | |
|---|---|
| **Dominio** | Seguridad |
| **Ubicación** | `supabase/sql/077_es_administrador_initplan.sql:383-386` (política por fila), `supabase/sql/110_supresion_propia_permiso_estado.sql:40` (trigger solo protege `rol`/`estado`), `supabase/sql/002_harden_security_definer_functions.sql:23` (`insert` sin `on conflict`), `prisma/schema.prisma:170` (`correo @unique`) |
| **Confianza** | CONFIRMED en código (sin grants por columna en ninguna migración ni script); no ejecutado contra una base |
| **Esfuerzo** | S |

**Qué está mal.** `perfiles_update_propio` deja actualizar la fila propia completa; no hay `GRANT UPDATE (columnas)` como sí lo hay en `comunidad_posts` (089:25). Con la llave pública y su sesión, el estudiante hace un `PATCH /rest/v1/perfiles?id=eq.<suyo>` con cualquier columna salvo `rol` y `estado`.

**Por qué importa** (se escala a P1 por tocar autenticación y datos personales):
- **Bloqueo de registro de terceros:** pone en su `correo` el de otra persona; cuando esa persona se registra, `handle_new_user` choca con el UNIQUE y su alta (correo o Google) falla.
- **Correo a direcciones ajenas:** bienvenida del canje (`src/actions/codigos-invitacion/canjear.ts:125-137`) y aviso de moderación (`src/actions/comunidad/eliminar.ts:53`) salen hacia el correo puesto; el admin y las exportaciones muestran el falso.
- **Píxel de rastreo:** `foto_url` externa se pinta con `<img>` en comentarios y en el detalle de usuario del admin → IP y navegador de otros estudiantes y de administradores. La CSP está en Report-Only (P2-9), así que nada lo bloquea.

**Reproducir (staging).**
```ts
await clienteEstudiante.from("perfiles").update({ correo: "victima@ejemplo.co" }).eq("id", miId); // hoy: sin error
await clienteEstudiante.from("perfiles").update({ foto_url: "https://evil.tld/p.png" }).eq("id", miId); // hoy: sin error
```

**Arreglo.** Ampliar el trigger (o pasar a privilegios por columna):
```sql
if (new.correo is distinct from old.correo or new.slug is distinct from old.slug
    or new.anonimizado_en is distinct from old.anonimizado_en)
   and not (private.es_administrador() or auth.role() = 'service_role'
            or coalesce(current_setting('uva.anonimizando', true), 'off') = 'on') then
  raise exception 'No permitido' using errcode = '42501';
end if;
if new.foto_url is distinct from old.foto_url and new.foto_url is not null
   and new.foto_url not like '%/storage/v1/object/public/avatares/' || new.id || '/%' then
  raise exception 'Foto no válida' using errcode = '42501';
end if;
```
Comprobar que la anonimización (075/120) y el cambio de nombre/slug legítimos pasen por la vía permitida. Añadir CHECK de longitud a `nombre`.

**Verificar.** Tres casos nuevos en `scripts/rls-test.ts` (correo, foto externa, `anonimizado_en`) → 42501; `npm run test:rls` en verde en CI.

#### P1-3 · El hook de correos comparte secreto con staging y arma el enlace con un origen que no valida

| | |
|---|---|
| **Dominio** | Seguridad / DevOps |
| **Ubicación** | `src/app/api/webhooks/supabase-auth/route.ts:106-116`; `SEND_EMAIL_HOOK_SECRET` en `.env.local` y `.env.produccion.local` (comparados por hash, sin imprimir) |
| **Confianza** | CONFIRMED en el código y en los archivos locales; PLAUSIBLE que Railway tenga el mismo valor |
| **Esfuerzo** | S (1 h) |

**Qué está mal.** `appOrigin = new URL(email_data.redirect_to, email_data.site_url).origin` sale del payload y no se compara con `siteUrl()`. El secreto que firma el payload es el mismo en staging y producción, y el de staging vive en cada portátil y en el panel de staging. Viola `docs/ops/salida-de-miembro-y-cambio-de-llaves.md:80-86`.

**Por qué importa.** Con el secreto de staging se firma un payload hacia producción con `redirect_to=https://evil.tld` y cualquier `user.email`: producción envía un correo real de «recupera tu contraseña» desde `mail.uvarq.com`, con DKIM/DMARC válidos y enlace al atacante. Phishing con la reputación de la marca y gasto de la cuota de Resend.

**Arreglo.**
```diff
- const redirectTo = new URL(email_data.redirect_to || "/", email_data.site_url);
- const appOrigin = redirectTo.origin;
+ const appOrigin = new URL(siteUrl()).origin;
+ const redirectTo = new URL(email_data.redirect_to || "/", appOrigin);
+ if (redirectTo.origin !== appOrigin) {
+   logError("webhook:supabase-auth", "redirect_to fuera del origen", undefined, { area: "webhook" });
+   redirectTo.href = new URL("/", appOrigin).href;
+ }
```
Y rotar `SEND_EMAIL_HOOK_SECRET` de producción para que sea único.

**Verificar.** Prueba en el test del hook: payload firmado con `redirect_to:"https://evil.tld/x"` → `actionLink` empieza por `siteUrl()`. Hash del secreto distinto en los dos archivos y en Railway.
