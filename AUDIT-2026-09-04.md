## Veredicto

**Todavía no, pero por primera vez el "todavía no" se mide en días, no en semanas.**

Lo que se hizo desde el 26 de agosto es sustancial y está verificado, no declarado: hay **CI real** con tres jobs que corren tipos, lint, 171 pruebas unitarias, las migraciones, los 63 scripts de RLS y `test:rls` contra una base real, más un gate que rechaza migraciones no reversibles; hay **un segundo proyecto de Supabase para staging** con las 124 pruebas de RLS en verde; hay **Sentry, healthcheck, redacción de PII en logs y un monitor de assets atascados de Mux**; hay **certificados de punta a punta**, rol `PROFESOR`, comentarios y contenido enriquecido, cada uno con su capa de RLS razonada; y hay **rendimiento y accesibilidad medidos** con Lighthouse donde antes no había un solo número. La calidad del SQL —el *porqué* documentado en cada policy, la explicación de por qué `curso_instructores_publico` no lleva `security_invoker`— está por encima de lo que se ve normalmente.

Lo que rompe primero son tres cosas pequeñas y una grande.

Las pequeñas: **dos controles de seguridad que el propio proyecto construyó a propósito no se sostienen**, porque ambos leen un header que el atacante escribe. Los límites por IP de `checkEmail` y de la verificación de certificados toman el primer valor de `X-Forwarded-For` — rotarlo los anula por completo (**P1-2**). Y los enlaces de los correos de autenticación —incluido el de recuperar contraseña— se arman con el header `Host` de la petición (**P1-1**); si la lista de *Redirect URLs* de Supabase Auth no está cerrada, eso es toma de cuenta por correo envenenado. Las dos correcciones son de una hora cada una.

La grande: **el formulario de registro obliga a marcar una casilla que dice aceptar los Términos y la Política de privacidad, y las dos rutas devuelven 404** (**P1-3**). No es "falta la política de privacidad" como en las dos auditorías anteriores; es que el producto ya está pidiendo un consentimiento informado sobre documentos que no existen, con datos personales entrando a la base. Con la Ley 1581 de 2012 de por medio, esa casilla no puede seguir así el día del lanzamiento.

Costo de lo que bloquea: **~4 días de una persona**, casi todo en la capa legal. Los dos P1 técnicos son medio día entre ambos.

**Puntaje: 62/100 (Aceptable con reservas)** — sube 12 puntos desde 50.
Más débiles: **Privacidad y cumplimiento (1/10)**, **Presencia web y SEO (4/10)**, **Dependencias (5/10)**.

### P1 — Críticos (4)

#### P1-1 · Los enlaces de los correos de autenticación se construyen con el header `Host` de la petición

- **Dónde** `src/actions/auth/recuperar.ts:12-19` y `:59` · `src/actions/auth/registro.ts:20-26` · `src/actions/auth/confirmar-enlace.ts:9-15` · `src/actions/auth/reenviar-verificacion.ts:15-22` · `src/app/api/webhooks/supabase-auth/route.ts:60-68`
- **Etiqueta** `CONFIRMED` que el header no validado se propaga hasta el enlace del correo. `PLAUSIBLE` que hoy sea explotable — depende de una configuración del dashboard que no pude ver.
- **Qué** Las cuatro Server Actions de autenticación repiten la misma función:

  ```ts
  async function getOrigin() {
    const headersList = await headers();
    const host = headersList.get("host");          // ← lo escribe el cliente
    const proto = headersList.get("x-forwarded-proto") ?? …;
    return `${proto}://${host}`;
  }
  ```

  Ese `origin` va directo a `resetPasswordForEmail(email, { redirectTo: \`${origin}/auth/confirm?next=/actualizar-password\` })`. Supabase lo devuelve como `email_data.redirect_to` al hook de envío de correo, donde `route.ts:60-61` hace `const appOrigin = redirectTo.origin` y arma el enlace final que recibe la persona.
- **Por qué importa** El flujo completo es: el atacante hace `POST` al formulario de recuperación con el correo de la víctima y `Host: evil.tld`; la víctima recibe un correo legítimo, firmado por el dominio real de U.V.A, con un botón que apunta a `https://evil.tld/auth/confirm?token_hash=…`; al pulsarlo entrega el token de recuperación al atacante. Eso es toma de cuenta sin phishing visible — el correo es auténtico.

  Lo único que hoy puede frenarlo es que Supabase Auth valida `redirect_to` contra su lista de *Redirect URLs* antes de generar el enlace. Ese control existe fuera del repositorio, no está documentado en `docs/ops/`, y nada en el código lo asume ni lo verifica. La app no debería depender de él.

  Agravante: `NEXT_PUBLIC_SITE_URL` está declarada como variable del proyecto (`docs/audit/rls-content-leak-2026-09.md §3.3`) y **no se usa en un solo archivo de `src/`** — `grep -rn "NEXT_PUBLIC_SITE_URL" src/` devuelve cero. La variable que resuelve esto ya está inventada y desconectada.
- **Reproducir**
  ```bash
  curl -X POST https://<dominio-real>/recuperar \
       -H 'Host: evil.tld' -H 'Origin: https://evil.tld' \
       --data 'email=<victima>@…'
  # Revisar el enlace del correo que llega: si el host es evil.tld, es P0.
  ```
  Antes de eso, la comprobación de dos minutos: **Supabase → Authentication → URL Configuration → Redirect URLs**. Si hay un comodín (`https://**`, `*`) o la lista está vacía, ya es P0.
- **Arreglar** Una constante de origen, no un header. Añadir a `src/lib/env.ts` (que hay que crear igual, **P2-6**) un `SITE_URL` obligatorio y sustituir las cuatro copias de `getOrigin()` por él:

  ```ts
  // src/lib/site-url.ts
  export function siteUrl(): string {
    const url = process.env.NEXT_PUBLIC_SITE_URL;
    if (!url) throw new Error("NEXT_PUBLIC_SITE_URL es obligatoria");
    return url.replace(/\/$/, "");
  }
  ```
  En `localhost` sigue funcionando con `NEXT_PUBLIC_SITE_URL=http://localhost:3000` en `.env.local`. Y, en paralelo, cerrar la lista de *Redirect URLs* de Supabase a los orígenes reales (producción + staging + localhost), como defensa en profundidad.
- **Verificar** Repetir el `curl` de arriba con `Host: evil.tld`: el enlace del correo debe apuntar al dominio real. Añadir una prueba unitaria que llame a `recuperar()` con un `Host` falsificado y afirme el `redirectTo` pasado a Supabase — es la clase de regresión que vuelve sola.

#### P1-2 · Los dos límites de tasa por IP se anulan con un header que el atacante escribe

- **Dónde** `src/actions/auth/check-email.ts:20-25` · `src/app/(public)/verificar-certificado/[codigo]/page.tsx:19-24`
- **Etiqueta** `CONFIRMED`
- **Qué** Las dos implementaciones (verbatim, duplicadas) hacen:

  ```ts
  const forwardedFor = headersList.get("x-forwarded-for");
  if (forwardedFor) return forwardedFor.split(",")[0].trim();   // ← el primero
  ```

  `X-Forwarded-For` se construye por acumulación: cada proxy **añade a la derecha**. El valor de más a la izquierda es exactamente el que envió el cliente, y no lo verifica nadie. Un atacante que mande `X-Forwarded-For: 1.2.3.4` obtiene la clave de límite `1.2.3.4`; cambiándola en cada petición nunca alcanza el umbral.
- **Por qué importa** Anula los dos únicos controles anti-enumeración del producto, ambos construidos a propósito y ambos listados como "Sostiene" en el modelo de amenazas de la auditoría anterior:
  1. **`check_email_provider`** es un oráculo de enumeración de cuentas por diseño (lo dice su propio comentario en `check-email.ts:13-18`): dice si un correo existe **y con qué proveedor entra**. Sin límite real, es un censo completo de la base de usuarios y un mapa de qué cuentas usan contraseña (atacables por *credential stuffing*) frente a las de Google.
  2. **`verificar_certificado`** devuelve **nombre completo del estudiante + curso + fecha** para cualquier código válido. Sin límite real, es enumeración de datos personales de todos los graduados. Hoy no hay certificados emitidos, así que el impacto es futuro, no actual — pero el módulo ya está en producción esperando el primero.

  Agravante de disponibilidad: `private.intentos_check_email` y `private.intentos_verificar_certificado` tienen `ip text primary key` y `on conflict (ip) do update`. Con la IP bajo control del atacante, cada valor distinto **inserta una fila nueva**, y ninguna de las dos tablas tiene rutina de limpieza (`limpiar_intentos_canjear_codigo` existe, pero es por usuario y solo para el canje). Es escritura ilimitada en la base desde un endpoint anónimo.
- **Reproducir**
  ```bash
  for i in $(seq 1 100); do
    curl -s -o /dev/null -H "X-Forwarded-For: 10.0.$((i/256)).$((i%256))" \
      "https://<dominio>/verificar-certificado/ABC$i"
  done
  # Ninguna devuelve la pantalla "Demasiados intentos".
  ```
- **Arreglar** Leer la IP **desde la derecha**, contando los saltos de proxy de confianza que hay delante (en Railway, uno), o usar la cabecera que inyecta la propia plataforma. Y extraer la función a un único módulo — hoy está duplicada literal en dos archivos, que es cómo una se arregla y la otra no:

  ```ts
  // src/lib/client-ip.ts
  const SALTOS_CONFIABLES = Number(process.env.TRUSTED_PROXY_HOPS ?? 1);

  export async function clientIp(): Promise<string> {
    const xff = (await headers()).get("x-forwarded-for");
    if (!xff) return "unknown";
    const cadena = xff.split(",").map((s) => s.trim()).filter(Boolean);
    // El proxy propio añade a la derecha: la última entrada es la única
    // que el cliente no pudo escribir.
    return cadena[cadena.length - SALTOS_CONFIABLES] ?? "unknown";
  }
  ```
  Confirmar antes cuántos saltos añade Railway: registrar el `X-Forwarded-For` crudo en una petición real y contar. Añadir además un barrido de filas caducadas (`delete from private.intentos_* where primer_intento < now() - interval '1 day'`) en el mismo cron que ya corre `certificados:notificar`.
- **Verificar** El bucle de arriba debe bloquear en el intento 21. Prueba unitaria de `clientIp()` con `"1.2.3.4, 10.0.0.1"` → debe devolver `10.0.0.1`, nunca `1.2.3.4`.

  ```sql
  for update using (auth.uid() = id_usuario or private.es_administrador())
  with check (auth.uid() = id_usuario or private.es_administrador());
  ```
  No restringe **qué** columnas se pueden escribir. Dos consecuencias: (a) tras un administrador marcar `eliminado = true` sobre un comentario abusivo, su autor puede hacer `PATCH /rest/v1/comentarios?id=eq.<suyo>` con `{"eliminado": false}` y republicarlo; (b) puede cambiar `id_leccion` y mover su comentario a una clase de un curso de pago al que no tiene acceso.
- **Por qué importa** La moderación es el único control sobre contenido escrito por usuarios en el producto, y hoy es reversible por el moderado. El (b) es menor pero desagradable: contenido inyectado en el hilo de un curso pagado por otros.
- **Arreglar** Un trigger `before update` que rechace el cambio cuando quien escribe no es administrador y toca algo que no sea `contenido`, o que impida devolver `eliminado` de `true` a `false`:
  ```sql
  create or replace function private.comentarios_restringe_update() returns trigger
  language plpgsql security definer set search_path = public as $$
  begin
    if private.es_administrador() then return new; end if;
    if old.eliminado and not new.eliminado then
      raise exception 'no se puede restaurar un comentario eliminado';
    end if;
    if new.id_leccion <> old.id_leccion or new.id_usuario <> old.id_usuario then
      raise exception 'columna no modificable';
    end if;
    return new;
  end $$;
  ```
- **Verificar** Dos casos nuevos en `scripts/rls-test.ts`: admin borra → autor intenta `eliminado=false` → rechazado; autor intenta cambiar `id_leccion` → rechazado.

#### P2-2 · Sin cabeceras de seguridad HTTP ni CSP (heredado, tercera auditoría consecutiva)

`next.config.ts` sigue sin `headers()`. Faltan `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`/`frame-ancestors`, `Permissions-Policy` y CSP. Hoy no hay un XSS conocido —`RichTextRenderer` evita `dangerouslySetInnerHTML` deliberadamente y valida URLs con `esUrlSegura`, que es la decisión correcta y hay que decirlo—, pero sin `frame-ancestors` la aplicación es enmarcable y sin CSP cualquier futuro XSS se convierte en robo de sesión. Los dominios a permitir ya se conocen: `*.mux.com`, `*.supabase.co`, `fonts.googleapis.com`, `fonts.gstatic.com`, `*.sentry.io`. Verificar con `securityheaders.com` = A. `CONFIRMED`.
